# 2026-08-24 — the agent asked a clarifying question and executed a mutation in the same turn

Status: **root cause identified — M2 confirmed, M1 ruled out.**
Session: `092d3c66-ac33-4021-91fa-8befa5420907` ("create an incident for mr with SD as : heloo i am testing…")
Turn: `turn_seq = 50`
Instance: `https://dev442675.service-now.com`, actor `admin`

## What the user saw

User message (Hinglish): *"acha ek kaam karo pripity ko change karke LOW kardo."* — "ok do one
thing, change the priority to LOW."

Two incidents were live in the conversation: parent `INC0010052` and child `INC0010053`. The
assistant rendered a clarifying question about which one to change, and then — with no
intervening user message — an `update_record` approval card for `INC0010053`
(`priority: "4"`, `sys_id 49b1d0538336cf50b939cc65eeaad3b7`, table `incident`) which reached
`approved` and executed. The Auto-approve checkbox was OFF.

Read-back honesty worked downstream: the write was reported `transformed`, not applied —
ServiceNow recomputed `priority` from `impact`/`urgency` and stored `1` where `4` was sent.
That part of the system did its job. The defect is upstream: **the turn should have ended at
the question.**

## Verdict: M2

> **M1** — a single assistant response carried both `content` and `tool_calls`.
> **M2** — the loop re-invoked the model after a text-only response; the second iteration
> emitted the tool call.

**M2 is what happened.** The continuation path is the **A6 stalled-turn guard** in
`server/src/agent/orchestrator.js`. It is the only code path in the repository that
re-invokes the provider on a completion carrying zero tool calls.

### Why M1 is ruled out

1. **The WI-8 guard was armed and did not fire.** `server/data/settings.json` at the time of
   the repro: `agent.autoApprove = false`, `agent.holdMutationsOnQuestion = true`.
   `detectQuestionWithMutation` runs on every completion that carries tool calls and records a
   `wi8_question_with_mutation` guard row when it holds. **No such row exists in this session.**
2. **The adapter cannot manufacture the split.** `providers/openaiCompat.js` maps `msg.content`
   and `msg.tool_calls` independently and returns `{ text, toolCalls }` with both preserved. A
   completion carrying both would have arrived at the loop carrying both, and would have hit
   the WI-8 guard rather than the A6 guard.

So the split is real, not an artefact of parsing.

## Why the A6 guard fired on a clarifying question

A6 exists for a measured failure: the model designs something, quotes the right sys_ids, and
then asks permission instead of calling the tool — the turn stalls and looks complete from the
outside. Its own comment states the intended boundary:

> A genuine clarifying question ("which of these two items did you mean?") does not match,
> because it does not ask for permission to proceed.

That boundary does not hold. A6 fires when **all** of: zero mutations this turn, the
assistant's text matches `ASKS_TO_PROCEED`, the user's text matches `IS_DIRECTIVE`, and it has
not already fired. On turn 50:

- `ASKS_TO_PROCEED` matched **`let me know`** — recorded verbatim in the guard payload. That
  pattern was widened deliberately (§32/A3) to catch "Let me know!" closing a stalled design.
  It cannot tell "let me know if you want me to build it" from "let me know **which** incident
  you meant" — both contain `let me know`.
- `IS_DIRECTIVE` matched **`change`**, present literally in "priority ko **change** karke LOW
  kardo".

Both halves fired on a question that was asking the user to *disambiguate a target*, not to
*authorise an action*. The nudge the guard then injected is written for the stall case and is
actively wrong for this one:

> *"You already have what you need. Call the tool now with the values you just described."*

The model did not already have what it needed — the target record was the open question. Told
by the harness that it did, it picked one and wrote to it.

The digest of the folded turn records the model's own view, which is not the harness's:

> **OPEN THREADS** — Need to set impact and urgency to Low for INC0010053 to achieve Low
> priority; **awaiting user confirmation** to apply those updates.

## The approval transition: how `approved` was reached

**There is no approval record.** This is a schema gap, stated explicitly as WI-1 requires.

Approval state today is an unresolved `Promise` held in a process-local `Map`
(`orchestrator.js`, `const live`), keyed by a `crypto.randomUUID()` that exists only for the
lifetime of the turn. When it resolves, the outcome is collapsed into a **single terminal
string** on `tool_events.approval` and `mutation_ledger.approval`. There is:

- no approval table,
- no state history,
- no timestamp of the transition (`tool_events.ts` is written *after* execution),
- **no source or actor field** — nothing distinguishes a user click from any other resolver.

### Every writer of approval state (complete enumeration)

| # | Site | Sets | Reachable when |
|---|----|----|----|
| 1 | `orchestrator.js` — `awaitApproval` timeout | `false` -> `'rejected'` | 5 min elapse with no resolution |
| 2 | `orchestrator.js` — `resolveApproval(sessionId, approvalId, approved)` | caller's boolean -> `'approved'` or `'rejected'` | called by #3 only |
| 3 | `routes/agent.js` — `POST /api/agent/approve` | forwards `req.body.approved` verbatim to #2 | any HTTP client that knows the `approvalId` |
| 4 | `orchestrator.js` — auto-approve branch | `'auto'` | `agent.autoApprove === true` |

`resolveApproval` is exported and has exactly one call site: the HTTP route. The route does no
validation — it forwards `approved` straight through and returns `{ ok }`. No server-side path
sets `'approved'` while `autoApprove` is false; the auto path writes the distinct value
`'auto'`, and the ledger row here reads `approved`, not `auto`, which is consistent with the
checkbox having been off.

### What the evidence can and cannot say

The `approved` on ledger row 27 was therefore produced by an HTTP `POST /api/agent/approve`
carrying `approved: true`. The client is the only known caller, so **a user click is by far the
most likely origin** — the 10.1 s window between the guard row and the executed write comfortably
contains a provider call, a human click, execution and read-back, and the user was actively
watching the session.

But it **cannot be proven from the persisted data**, because nothing records who resolved it or
when. Any process able to reach `POST /api/agent/approve` with the right `approvalId` would leave
an identical row. WI-4 closes this permanently by persisting `approved_source` and `approved_at`.

## Conclusions that drive the fix

1. **M2 is the mechanism.** The ask/act split came from the A6 stall guard re-invoking the
   provider after a text-only completion, not from one completion carrying both.
2. **WI-2's invariant, applied literally, would delete A6.** A6 is a deliberate,
   measurement-driven exception to "a text-only response ends the turn". The fix is not to
   remove it but to make it the *only* such exception, fenced so it cannot fire on a question
   aimed at the user — and to assert that fence in a test.
3. **WI-3's guard is real and already exists (WI-8), and it was not enough.** It only inspects a
   *single* completion. It has to survive the nudge: a turn that has already asked the user a
   question must not be allowed to write later in the same turn.
4. **WI-4 is unblocked and independent.** The approval record does not exist and must be built
   before "who approved this" is answerable at all.
